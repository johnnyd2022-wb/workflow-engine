# SKILL AUDIT — 2026-07-27

scope: concurrent multi-agent writes to one shared worktree
skills_audited: 6/49 (targeted, not a roster sweep) + 2 contract files
trigger: prior-session finding — two subagents independently converged on overlapping
fixes to the same files. Both converged correctly and the settled state was verified, so
no damage; the hazard was unaddressed.

## What was actually wrong

The incident was not bad luck, and it was not a missing lock. It was **two skills holding
contradictory beliefs about who is allowed to write**, with nothing in the system able to
detect the disagreement.

1. **`security-audit` believed remediation was mandatory.** Its SKILL.md said "every audit
   ends with remediation, not a report — section 5 is not optional", and its description
   said it "drives remediation to an MR". The routing table gives it `access: read`, and
   the chain spawns it *in parallel with `e2e-playwright`*, a writing stage. So the one
   declared parallel pair was, in practice, two agents that both believed they could patch
   the same tree. That is the collision mechanism.

2. **The read-only guarantee was real in exactly one of three execution modes.**
   `.agents/verification-chain.md` §3 claimed graders "physically cannot edit the code they
   judge", enforced "by construction". True only for Codex stages in `herdr-tabs` mode:
   - Claude read stages got `--permission-mode auto`, which **auto-approves** — it is not
     read-only. Verified live: a Claude agent under `auto` will happily write.
   - `herdr-adversarial` launches a plain interactive `codex` with no sandbox flag.
   - `subagents` — the mode the incident ran in — never consults `access` at all.
     `grep` confirms `scripts/agent_launch.py` is the *only* consumer of that field, and it
     is not on the subagent path.

3. **Concurrency was justified on quota grounds only.** §6 said "parallelism buys no
   capacity", which is true and beside the point. Nothing anywhere said *two writers in one
   worktree is unsafe*. The one file-ownership rule in the repo
   (`herdr-multi-agent-collab` §6) was scoped to cross-pane handoffs and keyed to a
   `files_touched` list that chain stages never produce.

## Honest limits

- `--disallowed-tools` withholds the edit tools but **not Bash**, which graders need for
  semgrep/pytest/git. A read stage that shells out can still write. Only Codex's
  `--sandbox read-only` closes that. This is stated in the code comment and in §3 rather
  than papered over — the structural guarantee is one writer per worktree, not the flag.
- `subagents` mode still has **no mechanical enforcement** and cannot have one: in-process
  subagents inherit the orchestrator's permissions and the Agent tool exposes no
  per-subagent permission flag. The mitigation is prompt-level plus the serial rule. This
  is a real residual risk and the reason fix #2 matters most — it removes the *opportunity*
  rather than trusting the instruction.

## Escalated — one human call

**Should `herdr-adversarial` mode launch its Breaker pane sandboxed?** Today §2 of
`herdr-multi-agent-collab` launches a plain `codex` TUI, deliberately, so the founder can
interact with it. That makes the Breaker write-capable while the Architect is also writing —
the same two-writer shape, mitigated only by the handoff protocol's `files_touched` lock.
Options: leave it (the protocol has held; a human is watching this mode by definition), or
launch the pane with a read-only sandbox and lose interactive use of it. I did not change
this: it trades away a workflow the founder uses, which is a product decision, not a repair.
