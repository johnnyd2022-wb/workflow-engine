## What the MR claimed, and what the harness can actually confirm

The MR reports 15.78s → 2.69s measured by Playwright against `whistlebird_test`'s real
data (243 rows). That measurement is not reproducible here — this skill's only sanctioned
measurement environment is the in-process E2E boot against the local test DB
(`.agents/autonomy.md`), whose fixture org is near-empty. Both numbers are honest; they
measure different things, and the difference is the finding below.

Deterministic before/after, same harness, same fixture — pre-MR run (2026-08-22,
committed `last-run.json`) vs post-MR run (today):

| route | queries before → after | backend_ms before → after |
|---|---|---|
| `/api/core/metrics` | 6 → **5** | 7.9 → 6.9 |
| `/api/core/inventory` | 9 → 9 | 10.5 → 12.4 |
| `/api/core/dashboard/summary` | 39 → 39 | 37.2 → 42.1 |
| every other measured route (27 of them) | unchanged | within noise |

**The single query-count change across the entire measured surface is `/api/core/metrics`
6 → 5.** That is the whole visible footprint of a change the MR measured at an 83%
end-to-end improvement. Nothing here contradicts the MR; the harness simply cannot see
what it fixed. Three reasons, all worth fixing in the guardrail rather than the MR:

1. **The fixture is empty; every bug the MR fixed was O(rows).** `get_metrics()` hydrating
   full object graphs to `len()` them, and `DAGTracer` re-loading the org's whole
   execution history per expired material, both cost ~nothing on an org with no history.
   A query-count budget calibrated on an empty org is blind to row-count regressions by
   construction.
2. **`/api/core/system-findings` had no budget at all** — the hottest endpoint on the
   page (5.1s → 1.8s per the MR, and ~1.1–1.4s of the remaining 2.7s), called by three
   independent widgets on every page load. Fixed in this change: added to `measure.api`
   and pinned.
3. **Three of the six fixes reduce the *number of requests a page makes***, not the cost
   of any one request (GET dedup, 3×→1× inventory fetch, dead `core.js` removal). The
   budgets file has no per-page request-count metric, so that dimension is unmeasured.

## Measured evidence for the follow-up

A throwaway probe (query counter around `run_expired_materials_check`, clones added to
grow the root count, then rolled back) on the **merged, post-MR** code:

```
expired-with-stock = 1   →  9 queries
expired-with-stock = 10  → 27 queries      slope: +2 queries per expired raw material
```

So the MR removed the per-root *bulk graph load* (the expensive part, correctly) but left
a linear ~2-queries-per-root residual. On `whistlebird_test`'s ~47 expired materials that
is ~100 queries inside one `/api/core/system-findings` request, and it is a lower bound —
the clones share provenance, so real materials touch the enrichment queries more.

The structural fix is one multi-root traversal instead of one per root: `traverse()`
already accepts `start_nodes: list[UUID]` and documents multi-root support. It is not a
drop-in — `find_impacted_by_expired_raw` attributes each impacted item back to its own
root and filters on that root's `expiry_date` — so it needs per-root edge attribution,
which is more than a perf edit. **Handed off to fix-bug**, with this row as the report.

Also measured and worth recording as a *negative* result: the shared tracer clears its
`_enrichment_cache` on every one of the N traversals (`clear_enrichment_cache` defaults
True and the loop does not pass False). Forcing it False saves **0 queries** (27 → 27),
because `_enrich_items_bulk` issues its three queries *before* consulting the cache. It
saves Python work only — not worth a change on its own.

## Not changed, reported to the human (merged code, review's call is not to patch it)

1. `CoreAPI.request()`'s in-flight GET dedup has no invalidation on mutation. A GET that
   is already in flight when a POST completes is still handed to the post-mutation
   refetch — `flows2-modals.js:106` and `core.js:285` both do
   `await createInventoryItem(...)` then `await loadInventory()`. Narrow window, but the
   deduped endpoints are the slow ones (~1.8s), which is exactly when it is widest. One
   line: clear `_inFlightGets` when a mutating request is issued.
2. `gunicorn.conf.py` sets `certfile`/`keyfile` only `if _cert_file.exists()`. With certs
   missing, the old `app.run(ssl_context=(cert, key))` raised `FileNotFoundError` at boot
   naming the file; gunicorn now silently binds plaintext, `force_https`
   (`app_factory.py:346`) 301-redirects everything to a scheme nothing serves, and the
   container fails its healthcheck for a reason the logs do not state. Fail loudly when
   `ENVIRONMENT` is test/production instead.
3. The dedup shares one parsed response object between callers. Today's three
   `getSystemFindings()` consumers all copy before mutating (`system-findings-notifications.js:461`
   uses `.slice()`), so this is latent, not live — worth a comment on `request()` so the
   next caller knows.

Verified sound, for the record: `count_executions_by_status` / `count_inventory_items_by_type`
