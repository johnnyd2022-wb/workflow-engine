# Performance-series review — MRs !187–!200

**Scope:** every change in !187 through !200, including the three open MRs (!197,
!199, !200) and the non-performance changes that share their migration chain.

**Verdict: changes required.** The series contains substantial, sound wins: composite
indexes, a read-through cache for the expensive expiry traversal, smaller response shapes,
keyset pagination, and deferred UI work all target real growth axes. The merged code and
the remaining open work should not be called clean, however. Five correctness/release
issues must be addressed first; two are direct opportunities to reduce the newly added
live-sync load.

This is a review report only. It deliberately does not alter behaviour or rewrite a
historical migration.

## Required changes

### P0 — replace the historical migration rewrite with a safe merge revision

At the time of review, `main` had two Alembic heads:

```
entity_events_seq_001          (from !196)
feature_subscriptions_001      (from !198)
```

`uv run alembic heads` and `alembic history --verbose` reproduce this directly. Both
branch from `system_findings_cache_001`.

Since this review began, !197 and !199 have merged that proposed rewrite. Fresh checkouts
now report one head, but the repair changed the parent of the already-merged
`feature_subscriptions_001` revision. A migration revision is part of a deployed
database's immutable history; changing its parent after it may have run makes
upgrade/downgrade behaviour dependent on which source tree happens to be present. This
review MR's first pipeline failed because it still had the original, correctly historical
two-head graph; merging current `main` reproduces the fresh-checkout one-head result.

Add one new empty merge revision instead:

```
revision = <new id>
down_revision = ("entity_events_seq_001", "feature_subscriptions_001")
```

Restore the historical parent, add the merge revision, and make all subsequent migrations
descend from it. Verify fresh `upgrade → downgrade → upgrade` and upgrades from databases
that record either the old two-head state or the temporary rewritten state. This is
release-blocking because a passing fresh migration check is not evidence that deployed
version tables remain safe.

### P0 — !197 exposes server templates by routing their whole directory through WhiteNoise

The now-merged !197 adds `app/core/frontend/inventory/` to `WhiteNoise.add_files()` at
`/static/inventory/`. WhiteNoise recursively publishes every file beneath that directory.
It does not preserve Flask's allowlist. That directory contains server-rendered templates
such as `add.html`, `add_manual.html`, `dispose.html`, and `view.html`, while the existing
route intentionally permits only `inventory-icon.svg` and `inventory-spa-header.css`.

Consequently the claim that the old filename/extension guards remain in effect is false:
the new WSGI layer handles `/static/inventory/add.html` before Flask. Keep the allowlisted
route, or move just the public CSS/SVG assets to a dedicated static-only directory before
registering it with WhiteNoise. Add a regression test that every previously disallowed
inventory filename stays non-200 (and that the two allowed assets retain their intended
content type and cache policy).

### P1 — !196's cursor is not safe under concurrent writers

`entity_events.seq` is a PostgreSQL identity/sequence value. Sequence allocation is not
commit ordered. If transaction A obtains sequence 100 and remains open, transaction B can
obtain and commit 101. A poll after the one-second settle window can return 101, advance
the client cursor to 101, and later never return A's committed 100 (`seq > 101`). The
one-second window lowers likelihood; it cannot establish correctness for a transaction
that runs longer than a second.

This matters more now because !199 expands the feed to dashboard, sourcemap, core hub,
and execute-step pages. A missed event leaves those screens stale until another matching
mutation occurs.

Replace the global sequence cursor with a commit-safe cursor design before expanding the
consumer set. A practical database design is a per-org feed counter allocated while
holding an org-row lock in the same transaction as the event: later writers for that org
cannot receive a cursor until an earlier writer commits or rolls back. Alternatively use
an outbox/dispatcher that assigns cursors after commit. Add a two-session test that holds
the first transaction open, commits the second, polls, commits the first, and proves both
events are delivered exactly once.

### P1 — !200's optimistic-concurrency check is a TOCTOU check, not an atomic guard

The three `If-Match` routes read `updated_at`, compare it in Python, then call the write
method later. `reorder_steps` makes this especially visible: its comparison uses the
request-scoped session, while the update uses a new `SessionLocal` transaction. Two
concurrent requests can both read the same token, both pass the comparison, and the last
commit still overwrites the first.

Move comparison and mutation into one transaction. Prefer an `UPDATE ... WHERE
id = :id AND updated_at = :expected` and treat a zero-row result as `409`; for reorder,
lock/read the process's steps with `FOR UPDATE` inside the same write transaction before
checking the structural token and applying all positions. Add a barrier-based two-client
test where both requests use the same initial token: exactly one must receive 200 and the
other 409. The current sequential tests prove stale detection only after a completed
write, not the race the feature is intended to prevent.

### P1 — cache failure handling can hide a failed check as a healthy system

Before !188, `CoreChecksRunner.run_all_checks()` turned a check exception into a flagged
`CheckResult` with `"Check failed: ..."`. The new `_run_live()` in
`system_findings_cache.py` logs an exception and omits the result. A failed live
`output_expiry`, `untracked_items`, or Compliant check can therefore disappear from the
dashboard/banner and let `system_status` report a better state than the pre-cache path.
An expensive cached-check exception can also escape before a cache row is written, rather
than following the runner's failure result contract.

Retain the old failure semantics in both paths: append a flagged failure `CheckResult`
for a live check failure and return the equivalent failure result for a cached-check
compute failure. Pin that with tests for one cached and one live failing check, including
the resulting `system_status` severity. This preserves performance without concealing a
compliance/operations failure.

## Performance follow-ups worth taking now

### P2 — make the intended changes-feed ETag path real

The server implements `If-None-Match` and returns 304 when `since >= head`, but
`live-sync.js` never stores or sends an ETag. On the steady state every visible browser
therefore runs both the `MAX(seq)` query and the empty events query every three seconds.
Persist the response ETag and send it with the next request for the same cursor. A clean
304 avoids the second query in the common no-change case. Add a browser/unit test that
asserts the second unchanged poll carries `If-None-Match` and receives 304.

### P2 — avoid running every live system check to serve expired materials

`/api/core/inventory/expired-materials` selects its result from `get_check_results()`.
That helper correctly merges cached expiry data *and every live check*, so this endpoint
now runs `untracked_items`, `output_expiry`, `output_ready_date`, and enabled compliance
checks even though its response discards them. Sourcemap then separately fetches several
of those results. Expose a narrow public cache accessor for the `expired_materials`
slice and have this endpoint use it; retain `get_check_results()` only for consumers that
actually require the complete set.

### P2 — !197's paged completed-execution query needs the matching index

The new page query is effectively:

```
WHERE org_id = ? AND process_id = ? AND status = 'completed'
ORDER BY created_at DESC, id DESC
LIMIT 26
```

Existing `ix_executions_org_created_id` supports tenant ordering, but not the
process/status predicates; `ix_executions_process_id` cannot satisfy the order. At scale
Postgres must scan/filter or sort much more history to return 25 rows. Add and verify a
composite index such as `(org_id, process_id, status, created_at DESC, id DESC)` against
a production-shaped fixture/`EXPLAIN (ANALYZE, BUFFERS)`. This is particularly important
because LiveSync can re-run the query repeatedly while a Batches panel is open.

## Scale limits that the specifications should state explicitly

- !197 calls the active-executions endpoint without a limit. “Few active runs” is a
  business expectation, not a bound enforced by the API. Either state an operational cap
  or paginate/render a bounded active list too.
- !195 reduced the create-process picker payload dramatically, but it still fetches the
  complete compact inventory list. The next scale step is a server-side search/typeahead
  with a limit and cursor; compact is a good interim representation, not an unbounded
  selection protocol.
- !187's three indexes are correctly aligned with the unfiltered tenant/time scans and
  have low write overhead. The audit-log optional filters (`user_id`, `action`, `entity`)
  are not all covered by `(org_id, timestamp)`. Do not add speculative wide indexes now;
  collect real filtered-query frequency and only add a targeted composite if an `EXPLAIN`
  demonstrates need.
