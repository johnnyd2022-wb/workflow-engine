## Findings

- F1 [fix] app/core/backend/reconciliation_service.py:564 (raise site: app/core/db/repositories/execution_repo.py:76); uncaught propagation confirmed at app/core/backend/reconciliation_routes.py:148-168
  **Cross-org `process_id` in Path B (`via-execution`) produces an uncaught 500 instead of the clean 400 every other cross-org input returns — a direct AC8 violation, and a verbose-error-to-client instance of the exact class already patched once in this file.** Already fixed by commit `b2b5144` (verified 2026-08-08 by findings-sweep — see `.agents/reports/fix-bug/2026-07-31-reconciliation-cross-org-process-id.md`).

  `reconcile_via_execution` calls `exec_repo.create_execution(org_id=org_id, process_id=process_id, commit=False)` at line 564, inside a `try` block that ends `except Exception: session.rollback(); raise` (lines 679-681). `ExecutionRepository.create_execution` raises a bare `ValueError` when the process doesn't belong to the caller's org (`execution_repo.py:76`: `raise ValueError(f"Process {process_id} not found or does not belong to org {org_id}")`). The service's `except Exception` clause re-raises it unchanged — it does not convert it to the `{"error": ...}` dict shape every other validation failure in this function uses (compare: `"Untracked item not found"`, `"Step not found in this process"`, both returned as clean dicts). The route (`reconciliation_routes.py:148-168`) has no `try/except` around the `reconcile_via_execution(...)` call — only a `try/finally` for `session.close()` — so the `ValueError` propagates straight out to Flask's own exception handling. There is no app-wide `errorhandler` for `ValueError`/`Exception` (`app/api/app_factory.py` registers only `@app.errorhandler(401)`), so this is a genuinely unhandled exception at the WSGI layer.

  repro/evidence: reproduced directly against the test DB (org A caller, `process_id` belonging to org B, valid `untracked_item_id` in org A) via both a direct service call and a full HTTP round trip through `create_app()`'s test client (mirroring the existing `tests/test_reconciliation_routes.py` pattern):
  ```
  ValueError: Process f4dabddd-... not found or does not belong to org 781ea8c5-...
  ```
  raised from `execution_repo.py:76`, propagating unhandled through `reconciliation_routes.py:150` (`full_dispatch_request` → `dispatch_request` → view function → uncaught).

  Impact:
  1. **AC8 violation.** The spec requires cross-org `process_id` to "fail exactly as if it didn't exist" — every other AC8 path (`untracked_item_id` via `get_inventory_item_by_id_for_update`, `step_id` via the post-creation `all_steps` scan) does this correctly and returns a clean 400 with `{"error": "..."}`. This one path instead produces a 500, a distinguishable status-code signal that a cross-org `process_id` behaves differently from a same-org-but-wrong `process_id`/`step_id` combo (which cleanly 400s as `"Step not found in this process"`). That distinguishability is itself a (weak) tenant-existence oracle, and it's a functional contract break regardless. Already fixed by `b2b5144` — the route now returns a clean 400.
  2. **Verbose-error-to-client, worse than the already-patched case.** `app/config/local.ini` and `app/config/test.ini` both set `debug = true` (only `prod.ini` sets `debug = false`); the app server this audit ran against (`https://localhost:8005/`) is running under `local.ini`. With Flask debug mode on, an uncaught exception renders Werkzeug's interactive debugger/traceback — leaking the org_id and process_id values, full stack trace, source snippets, and file paths. `tests/test_reconciliation_routes.py` already has a regression test for a narrower instance of this exact class (raw `UUID(...)` parse-exception text reaching the client); this is the same vulnerability class via a different code path, and it's not caught by the existing `bize-verbose-error-to-client` learned semgrep rule (`.semgrep/rules/learned.yml`), which only matches an `except E as e:` clause that interpolates `{e}`/`str(e)` directly into a `jsonify(...)` call — it does not match an exception that is never caught by the route at all. This finding needs its own rule (see below); the existing one is silent on it by design (confirmed: 0 semgrep findings on the scoped files in this run). Already fixed by `b2b5144` — no traceback reaches the client now.
  3. Even in prod (`debug=false`, no traceback leak), it's still a bare, unlogged-by-this-code 500 for what is a routine, expected input-validation case (a user submitting a `process_id` from the wrong org) — worse operational visibility than the deliberate `{"error": ...}` responses everywhere else in this file. Already fixed by `b2b5144`.

  patch: not applied (chain-stage grader — read-only). Recommended fix shape: catch `ValueError` from `exec_repo.create_execution(...)` in `reconcile_via_execution` (or catch it in the route) and return `{"error": "Process not found"}` → 400, consistent with the `"Untracked item not found"` / `"Step not found in this process"` shape already used by this function, without echoing the raw exception text (same discipline as the existing UUID-parse fix). Also worth widening the existing `bize-verbose-error-to-client` learned rule (or adding a sibling rule) to catch "domain-check `ValueError` raised inside a repository/service call and not converted to a Flask `{"error": ...}` response before reaching a route" — the pattern that would have caught this before an agent had to find it by tracing execution paths by hand.
  rule_added: none (chain-stage grader does not write `.semgrep/`; recommend `fix-bug` add a sibling rule to `bize-verbose-error-to-client` per the note above when it patches this)
  route: **fix-bug**, flagged as security/tenant-isolation (per security-audit skill's routing table: tenant isolation / auth bypass / data leak → fix-bug, red-then-green repro test first — "org A process_id against org B fails as 400, not 500" must fail before it passes)

## Attempted but clean

- **Tenant isolation on `untracked_item_id`** (all three write/read paths): every lookup goes through org-scoped repository calls — `get_inventory_item_by_id_for_update(item_id, org_id)` and `get_inventory_item_by_id(item_id, org_id)` in `app/core/db/repositories/inventory_repo.py:276-290` both filter `InventoryItem.org_id == org_id` in the query itself (not a post-hoc check), so a cross-org `untracked_item_id` correctly 404-shapes as `{"error": "Untracked item not found"}` → 400, with no distinguishing signal versus a genuinely nonexistent ID. Verified in `reconcile_via_addition` (line 400-402), `reconcile_via_execution` (line 522-524), and `reconcile_output_to_untracked_reduce_only` (line 706-708).
- **Tenant isolation on `step_id`** (`via-execution`): `step_id` is matched against `all_steps`, which is queried scoped to the just-created execution (`ExecutionStep.execution_id == execution.id`, and that execution was created under a process already verified to belong to `org_id`) — a `step_id` from another org's process simply never appears in `all_steps`, producing the clean `"Step not found in this process"` 400 with no cross-org signal. This path is correct; only the `process_id` check (F1) leaks via exception instead of a clean return.
- **`matching-untracked` (AC1, read path)**: `get_matching_untracked` sources items via `InventoryRepository.get_untracked_items(org_id=org_id, ...)` (org-filtered at the query level, `inventory_repo.py:302-317`), and both enrichment steps (`_enrich_matching_untracked_with_step_metadata`, `_enrich_producing_step_name`) re-filter by `org_id` when joining `Execution`/`Process` data. One sub-path is worth a hardening note without being a live leak: `_quantity_consumed_from_item_in_execution` (`reconciliation_service.py:149-153`) queries `ExecutionStep` by `execution_id` alone, with no `org_id` filter, when `get_matching_untracked` is called with a caller-supplied `execution_id`. In practice this isn't exploitable as a cross-org leak because the result is only used to check whether the caller's *own* (already org-scoped) `item.id` appears in that execution's `actual_inputs` — a foreign org's `ExecutionStep.actual_inputs` should never reference an inventory item belonging to a different org, so a cross-org `execution_id` yields `consumed == 0` indistinguishably from a nonexistent one. Flagged as a **defense-in-depth recommendation** (add `.join(Execution).filter(Execution.org_id == org_id)` to that query), not a `fix` finding — no current failure scenario found where it changes response content or timing in an attacker-observable way. Not routed anywhere; noting it here so it isn't silently lost.
- **Mass assignment**: all three service functions take explicit named parameters; routes pull individual fields off `request.get_json()`/`request.args` (`reconciliation_routes.py`) — no `Model(**request.json)` or looped `setattr`.
- **Injection**: all queries are SQLAlchemy ORM with bound parameters; no raw SQL, no `subprocess`, no `| safe`/`Markup()` on user input, no file-path handling in this slice.
- **SSRF / uploads**: not applicable — no external URLs or file uploads in this slice (matches spec's "External surfaces: none").
- **Secrets / config**: gitleaks found 0 leaks (925 commits, ~24.78MB scanned). No secrets in the scoped files.
- **CSRF / CORS**: none of the three routes are in the `CSRFProtect` exemption list in `app/api/app_factory.py:382-383` (only `auth.*` and the two telemetry-ingest endpoints are exempted), so Flask-WTF's global CSRF protection applies to the two POST routes as expected; the SPA sends `X-CSRFToken` per `WTF_CSRF_HEADERS`.
- **Auth on every route**: all three routes (`matching-untracked`, `via-addition`, `via-execution`) carry `@requires_auth`. No bare routes found.
- **AC3's 400-for-404 status code choice** (`if "error" in result: return ..., 400` uniformly in the route, even for not-found cases) — confirmed as existing, spec-documented, intentional-by-omission behavior (spec's own "Assumptions" section already flags this as a finding-to-call-out rather than a bug to fix). Not re-raised as a new finding here since it's already tracked and isn't a leak — just a status-code style choice (404-shaped errors returned as 400).
- **AC5/AC6 concurrency and invariant guards**: `get_inventory_item_by_id_for_update` uses `.with_for_update()` (row lock) before every balance read in the two mutating paths and in `reconcile_output_to_untracked_reduce_only`; `_assert_reconciliation_invariants` is called before every commit and raises (not clamps) on a negative balance. Both match spec AC5/AC6. Note: this assertion, like `create_execution`'s org check, sits inside `reconcile_via_execution`'s blanket `except Exception: session.rollback(); raise` — if it ever fired in production it would also surface as an uncaught 500 rather than a clean error, but this is a "should never happen" defensive assertion (not attacker-reachable the way the `process_id` org check is), so it's noted here rather than raised as its own finding.
