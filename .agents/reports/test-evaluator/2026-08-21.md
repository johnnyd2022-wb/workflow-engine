## findings

`test_ac4_starting_abv_of_100_is_a_valid_given_value` :: docstring claims the test
exercises `_mass_fraction_for_abv`'s `abv_pct >= 100.0` fast path (line 62-63, "the exact
w=1.0 case, no bisection") and that this is what's being proven, but neither assertion
depends on that function's return value — `math.isfinite(water_to_add_ml)` passes even
when the fast path returns a wrong mass fraction (probed: `1.0` → `0.5`, stayed green).
The test is a legitimate, falsifiable guard for the *validation-acceptance* boundary
(starting_abv=100 isn't rejected — confirmed by the line-94 mutation going red), but it is
mis-scoped for the coverage line it was written to close (line 63) and overclaims in its
own docstring what it proves about the solver's boundary arithmetic. To actually cover
line 63's behavior, the test would need to assert something that depends on the *value* of
`w_start` — e.g. pin `water_to_add_ml` (or `w_start` via a direct call to
`_mass_fraction_for_abv(100.0)`) to its expected numeric value, not just check it's finite.

## verdict

gamed — `test_ac4_starting_abv_of_100_is_a_valid_given_value` closes coverage on line 63
by executing it, but its assertions don't depend on what that line returns (probed: line
63's `return 1.0` mutated to `return 0.5`, test stayed green). It is a real test of a
different, narrower claim (the line-94 acceptance boundary), just not the one its own
docstring and coverage-closing purpose claim. The other 3 tests are valid and stay
