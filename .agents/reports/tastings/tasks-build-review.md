## Implementation and boundary checks

- **Typed persistence and compatibility:** CRMTask has a general default and an allowed-value constraint. The draft migration backfills only same-org linked tastings. Ordinary clients omitting the field retain general behavior. General/call/email creation and editing use the existing service; invalid/non-string types and attempts to attach tasting through ordinary editing are rejected. The existing tasting service now creates the same single linked task as type tasting; it does not create a second preliminary record.
- **Unified transaction boundary:** POST `/api/crm/tasks` branches only on the explicit tasting type, requires exactly the type plus nested tasting object, rechecks active NZ Alcohol subscription, and delegates to the existing transactional save path. Nested fields still pass its strict validation and same-org reference checks. Validation and integrity failures roll back rather than leaving an orphan task. The subsequent serialization returns the persisted linked task and event. No stock mutation is added to task creation/completion.
- **Read and mutation authority:** existing CRM endpoint policy supplies sales permissions and the selected-site registry explicitly classifies the new direct task GET. Dispatch retains both sales.record and inventory.adjust. Generic task edits/deletes and lane changes still reject a linked tasting before mutation, independently of submitted task_type. Unsubscribed organizations cannot create through the generic task route as a shortcut around the specialized gate.
- **Lapse visibility:** the shared visibility predicate hides both typed tasting rows and relationship-linked rows when NZ Alcohol is inactive. It is used before Core list/archive limits, CRM lists/contact-filtered lists, direct GET and customer last-contact aggregation. Customer detail uses the filtered task repository. I searched the actual CRMTask query sites rather than assuming the top-level list covered them. Existing tasting accounting history is retained, and specialized routes keep their subscription gate.
- **Draft switching:** ordinary title/notes/assignee/customer/day are mapped explicitly to specialized fields without an intermediate save. The captured specialized draft retains venue, times and allocation metadata; switching back merges common fields into the existing ordinary draft so priority/status are preserved. Fresh New task clears the old specialized draft. Raw long text is assigned without truncation, and submit checks the specialized length limits before sending. Unassigned remains unassigned rather than choosing a rep implicitly.
- **One workspace:** existing Board/List/Week and shareable type/view URL state operate on the same typed records. Inline detail handles tasting click/done/delete actions; dragging is suppressed and server guards remain authoritative. Writes dispatch `tasting-changed` and refresh task data without navigating or resetting filters/views. Stock/choice calls are lazy; merely initializing Tasks does not load a separate tasting event list. The old page is now a validated, tenant/subscription-scoped compatibility redirect.
- **Old finished links:** Core now links to CRM task ID; Tasks has a scoped direct GET fallback when an old record is absent from the currently loaded collection, so it can resolve the correct tasting detail. The direct reader applies the same lapse filter. No unscoped UUID lookup or client-controlled redirect destination was introduced.
- **Stock/excise regression scope:** the underlying dispatch/finalisation/cancellation and frozen excise calculation code is unchanged apart from setting the linked task type at creation. Pool reuse continues to reserve the existing lot, and the specialized controller sends only the established allocation/lifecycle payloads.
