# Live-sync architecture — near-real-time SPA off the `entity_events` change feed

## The problem

Pages like flows2, `/core`, the sourcemap and the dashboard load their data once and only
re-fetch after a mutation *the current user* makes. At 100 orgs × 2–10 concurrent users
that produces guaranteed daily friction that reads as bugs:

- **Shared process, two people.** A has flows2 open on the Batches tab; B starts a batch /
  completes a step / adds inventory for that process. A's page never updates — list, the
  `executions-badge`, inventory quantities all frozen. "I did that 10 min ago, why don't
  you see it?"
- **The all-day tab.** flows2 left open on a second monitor shows the morning's data at
  4pm; someone makes an ops call on stale state.
- **Stale inventory → wrong decision.** A colleague's execution consumed the last of a raw
  material; you still see it available.
- **No refresh affordance.** Tab switches are 0-fetch by design, so the only way to
  refresh is a full page reload — and users have to *know* to.
- **Sticky errors.** A transient `loadInventory()` failure leaves a dead panel + a toast,
  no retry.
- **Lost updates.** B's stale page toggles a process draft→ready; last-write-wins silently
  reverts A's change; neither is told.

Separately, the flows2 per-process calls (`getExecutions(?process_id=)`,
`getInventory(?process_id=)`) are **unbounded** — fine on the test org, multi-MB and janky
for a bottling line with 700+ executions.

## The design — polled change feed, transport-swappable

**Why not SSE/WebSocket now.** The app is synchronous Flask on gunicorn `gthread`. A held
SSE/WS connection occupies a worker thread for its whole lifetime; at 1000 concurrent
users you need ~1000 threads or async workers — a stack rewrite touching every blocking
DB call. A cursor-polled feed needs **zero new infra**, is one indexed query per client
per few seconds (~300 qps of trivial lookups at that scale — nothing for Postgres),
degrades gracefully, and — critically — the **client contract (`LiveSync.subscribe`) is
transport-agnostic**, so SSE/WS can replace the poll later (after an ASGI move) without
touching a single feature file.

`entity_events` is already the event-sourcing spine: `EventWriter.emit()` is the single
choke point, every mutation writes one row *in the same transaction* as the mutation.
This design just exposes it as a feed.

## Status

**Phase A shipped** (feat/live-sync): the change feed + `LiveSync` + flows2 + the badge. Measured: a batch started by user B appears on user A's open flows2 in ~1.9 s, no reload. Feed query is an index scan, ~0.3 ms.

## Work plan (tick as landed)

### Phase A — the backbone + flows2 + badge  `[x]`  (feat/live-sync)

**A1. `entity_events.seq` monotonic cursor — `[x]`** (`entity_events_seq_001`)
`created_at` isn't unique and the PK is a random UUID, so neither gives a total order.
Migration: `ALTER TABLE entity_events ADD COLUMN seq BIGINT GENERATED BY DEFAULT AS
IDENTITY` (Postgres backfills existing rows in heap order — historical order doesn't
matter, only recent events do) + `CREATE INDEX ix_entity_events_org_seq (org_id, seq)`.
Model gets `seq = Column(BigInteger, ...)`. Not-live, so a plain in-txn migration is fine.

**A2. `GET /api/core/changes` — `[x]`** (`changes_feed.py`; key extraction in SQL; entity-type allowlist keeps `user.*` out; 1 s settle window; EXPLAIN: index scan on `(org_id, seq)`, ~0.3 ms/poll)
`@requires_auth` + `@requires_org_scope`. Params: `since` (int seq; omitted = bootstrap),
`limit` (default 200, max 500). Query:
`WHERE org_id=:org AND seq > :since AND created_at <= now() - interval '1 second'
 ORDER BY seq LIMIT :limit+1`
The 1 s settle window covers the sequence-gap race (a txn assigned an earlier seq that
commits after a reader passed it). Response:
`{ "cursor": <max seq returned, or :since if none>, "has_more": bool,
   "events": [ { "seq", "event_type", "entity_type", "entity_id", "at",
                 "keys": { process_id?, execution_id?, execution_step_id?, step_id?,
                           inventory_item_id?, source_execution_id? } } ] }`
`keys` is extracted from `payload` (routing ids only — no state, no PII). `ETag:
"<cursor>"`; `If-None-Match` == head → `304`. Bootstrap (`since` omitted) returns the
current head `cursor` and `events: []`.

**A3. `LiveSync` client — `[x]`** (`live-sync.js` in base_spa; visibility-aware poll, backoff, backlog drain, `key`-scoped subscribe, `live-sync:tick`)
- Singleton on `window.LiveSync`. `start()` bootstraps the cursor, then a poll loop:
  visible → 3 s; hidden → paused; `visibilitychange`→visible and `online` → immediate
  poll; on error → exponential backoff 5 s → 60 s, resume on success.
- `LiveSync.subscribe({ match(evt) -> bool, onChange(evts) -> void, key? })` →
  `unsubscribe()`. Each poll: pull new events, advance cursor, and for every subscriber
  collect the matching subset; if non-empty call `onChange(subset)` **once** (one call per
  poll per subscriber). `key` de-dupes a component that re-subscribes on hx-boost re-init.
- Emits a `live-sync:tick` CustomEvent on `document` after each poll. Lives on `window`
  and binds on `document.body`/`window` so it survives boosted navigation.
- Never throws into the page; a poll failure is logged once and retried.

**A4. Wire flows2 — `[x]`** (subscribe on init; matches process/execution/inventory events for this process; debounced refetch of executions+inventory + an "updated" flash; also added the missing `htmx:afterSettle` re-bootstrap so flows2 survives boosted nav)
`flows2InitPage` calls `LiveSync.subscribe({ key: 'flows2:' + processId, match, onChange })`.
`match(evt)` = `evt.keys.process_id === processId || evt.entity_id === processId ||
myExecutionIds.has(evt.keys.execution_id) || myExecutionIds.has(evt.keys.source_execution_id)`.
`onChange` = refetch executions + inventory (bounded — see Phase C), re-render the active
panel, flash a subtle "updated just now" affordance. Unsubscribe on teardown; the `key`
makes re-init replace cleanly.

**A5. Wire the sidebar notification badge — `[x]`** (`LiveSync.subscribe` on inventory/execution/process events -> `refreshBadge()`; only re-fetches system-findings when something could actually have changed the count)
`refreshBadge()` runs on `live-sync:tick` (when the tick carried a findings-relevant
event) instead of its own `htmx:afterOnLoad` blanket hook. Cuts redundant
`/api/core/system-findings` fetches and makes the badge live.

**A6. Tests — `[x]`** (`test_changes_feed.py` — 8; `tests/e2e/test_live_sync.py` — two browser contexts, B starts a batch, A's flows2 badge ticks 0->1 within a poll, no reload)
- `test_changes_feed.py`: bootstrap returns head + empty; `since` returns only newer
  events in seq order; `keys` extraction per event type; cross-org isolation; 304 on
  `If-None-Match`; the settle window (an event with `created_at` inside the last second
  is withheld).
- e2e: two browser contexts, same org — B mutates, A's flows2 Batches list updates
  within one poll without a reload.

### Phase B — wire the rest of the SPA  `[ ]`

`/core` hub (replace the my-mutation-only refresh), sourcemap, inventory list/view,
dashboard, execute-step page (warn if the execution changed underneath). Each is a
`LiveSync.subscribe` + a targeted refetch. Own MR.

### Phase C — bound the growing payloads  `[ ]`

- `list_executions` `?process_id=` path gains `?limit` + keyset cursor (reuse the !183
  `_encode_list_cursor` helpers). flows2 Batches tab: first page + "Load more" / infinite
  scroll; the badge count comes from a `count`, not `len(list)`.
- flows2 inventory → `getInventory(processId, { compact: true })`.
- flows2: render the Structure panel on load; render Batches / Inventory only when their
  tab is first opened (keeps "instant after first open"), then keep them warm.
- flows2 panel load errors → inline "couldn't load — retry" per panel, not a dead panel.
- A manual refresh control on each volatile panel.

### Phase D — optimistic concurrency  `[ ]`

`updateProcess` / `updateStep` / reorder accept `If-Match: <updated_at>` (surfaced in the
GET, echoed by the client). Mismatch → `409` with the current entity. Client: "Someone
else changed this — showing the latest", reload the panel. Own MR; needs the version
surfaced end to end.

## Non-goals / explicitly deferred

- SSE/WebSocket transport — designed *for*, not built now (needs ASGI). The client
  contract won't change when it lands.
- Field-level CRDT / operative-transform collaborative editing — out of scope; last-write
  -wins + a 409 is the right level for this product.
- A Redis/broker fan-out — the polled Postgres feed is sufficient at the stated scale;
  revisit only past ~10k concurrent users.
